# Ship Phramer signed through the Microsoft Store

The cheapest path to a trusted, Microsoft-signed Phramer is to publish a **free MSIX through the Microsoft Store from a free individual developer account**. The total cash cost is **$0**: registration is free, a free app needs no payout or tax setup, and the Store re-signs every certified package with a Microsoft certificate, so you buy no code-signing certificate ([Free developer registration](https://learn.microsoft.com/windows/apps/publish/whats-new-individual-developer); [App package requirements: code signing](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements)). Phramer cannot ship as a plain repackaging of today's MSI binary, though. Five behaviours rely on registry writes, self-elevation or `msiexec`, and all five either break silently or breach Store policy once the process has package identity: the self-updater, the Print Screen takeover, ms-screenclip registration, Run-key autostart and path-based restart. The plan is therefore a **compile-time Store edition** (`PHRAMER_STORE_BUILD`) plus a small runtime package-identity helper. A hand-written `AppxManifest.xml` is packed by `makepri`/`makeappx` in a separate CI job, verified on your own Windows machine with a self-signed test certificate and WACK, then submitted through Partner Center, where certification takes up to three business days ([App certification process](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/app-certification-process)). The MSI and ZIP builds stay byte-for-byte unchanged and keep serving existing users. Three risks remain open, and each has a working fallback: whether Windows routes Print Screen to a *packaged* ms-screenclip handler and whether reviewers accept it, whether the Print Screen registry value is virtualized, and the Flameshot name and listing overlap. The report ends with a seven-phase work plan. Each phase states who does it (repository and CI, or you personally on Windows and in Partner Center) and the acceptance criteria that close it.

## The Store route costs nothing and removes the signing problem

Microsoft's new individual onboarding at storedeveloper.microsoft.com **waives the old $19 fee**. It verifies you with a government ID and a selfie, then gives "instant access to Partner Center" ([Free developer registration](https://learn.microsoft.com/windows/apps/publish/whats-new-individual-developer); [Open a developer account](https://learn.microsoft.com/windows/apps/publish/partner-center/open-a-developer-account#step-by-step-flow)). That URL is the only entry point for the free flow; other paths show the legacy flow. Individual accounts must use a personal Microsoft account and suit hobbyist, non-commercial distribution, which describes Phramer ([Get started with Microsoft Store](https://learn.microsoft.com/windows/apps/publish/get-started)). "If you only plan to list free offers, you don't need to set up a payout account or fill out any tax forms" ([Set up payout and tax profiles](https://learn.microsoft.com/partner-center/account-settings/set-up-your-payout-account)). Packages "don't have to be signed with a certificate rooted in a trusted certificate authority… The Microsoft Store will automatically re-sign your MSIX/AppX packages with a Microsoft certificate" ([App package requirements](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements)). The SmartScreen warning that the unsigned MSI triggers today has no counterpart on the Store path, because the user never downloads an unsigned installer. That claim is an inference from the re-signing model; no Microsoft page states it in those words.

Three facts constrain how the Store edition fits the existing release discipline. First, **the fourth version field is reserved and must be 0**, and the others must lie in 0–65535 with a non-zero first field ([Package version numbering](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/app-package-requirements#package-version-numbering)). The repo's `set(FLAMESHOT_VERSION 15.0.0)` (`CMakeLists.txt:4`) and its `MAJOR.MINOR.PATCH` guard (lines 14–22) therefore map mechanically to `15.0.0.0`. The Store serves the highest applicable version, so CLAUDE.md's "versions must strictly increase" rule now protects Store users too, and a Store-only hotfix needs a PATCH bump that also moves the MSI. Second, **Store Policies 7.20 take effect on 22 October 2026**. Its changes are almost all about games and Xbox; the two that touch Phramer are 11.11 (keep the age rating accurate for the product's lifetime) and 11.12 (user-generated content) ([Store Policies](https://learn.microsoft.com/windows/apps/publish/store-policies); [Change history](https://learn.microsoft.com/windows/apps/publish/store-policies-change-history)). Third, the MSI is not retired. It keeps its unsigned SmartScreen experience and its GitHub updater for users who stay on it, and the Store listing becomes the recommended channel. Signing the MSI itself (for example with Azure Artifact Signing, which Microsoft suggests for non-Store distribution) is a separate, paid decision that this plan does not need ([MSIX troubleshooting: SignTool in CI](https://learn.microsoft.com/windows/msix/msix-troubleshooting-guide#signtool-not-found-in-ci-cd)).

The precedent is good. GPL-3.0 desktop software is routinely accepted. ShareX, a GPLv3 screenshot, annotation and upload tool, is in the Store as product 9NBLGGH4Z1SP, and GIMP, Inkscape and Krita are published by their own projects ([ShareX on Microsoft Store](https://www.microsoft.com/en-us/p/sharex/9nblggh4z1sp); [GIMP on the Microsoft Store](https://www.gimp.org/news/2022/06/18/gimp-2-10-32-on-microsoft-store/)). KDE ships Kate and Okular as Store MSIX packages built from a hand-written AppX template with `EntryPoint="Windows.FullTrustApplication"` and a 17763 minimum "because Qt requires 1809" ([KDE Craft AppxManifest template](https://raw.githubusercontent.com/KDE/craft/master/bin/Packager/AppxManifest.xml)). Nothing in Phramer's stack is unusual for a Store full-trust app.

## Five integrations break under package identity and need a Store edition

A packaged full-trust app runs at medium integrity with no AppContainer, so most of Phramer behaves exactly as it does today. Global hotkeys through `RegisterHotKey`, the tray icon, GDI capture, DWM window enumeration, UI Automation and Windows.Media.Ocr need no capability. The `graphicsCapture*` capabilities apply only to Windows.Graphics.Capture, which Phramer does not use ([App capability declarations](https://learn.microsoft.com/windows/apps/package-and-deploy/app-capability-declarations#general-use-capabilities); [Windows apps: packaging and process](https://learn.microsoft.com/windows/apps/get-started/intro-pack-dep-proc#app-capabilities)). The Snipping Tool video handoff in `src/utils/snippingtool.cpp` keeps working unchanged. `LaunchUriAsync` with `TargetApplicationPackageFamilyName` is documented as callable from desktop apps, and targeting the package family means a packaged Phramer that owns ms-screenclip cannot receive the link back ([Launcher.LaunchUriAsync](https://learn.microsoft.com/uwp/api/windows.system.launcher.launchuriasync); [TargetApplicationPackageFamilyName](https://learn.microsoft.com/uwp/api/windows.system.launcheroptions.targetapplicationpackagefamilyname)). The rest is the problem. The package directory under `C:\Program Files\WindowsApps` is read-only. "All writes under HKCU are copied on write to a private per-user, per-app location". Newly created AppData files are redirected to a per-package store ([Understanding how packaged desktop apps run](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)). And "apps that require elevation for any part of their functionality won't be accepted into the Store" ([Prepare to package a desktop application](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare)).

### One compile flag removes code, one runtime check picks the path

The edition needs two mechanisms because each covers a gap in the other. A CMake option `PHRAMER_STORE_BUILD` keeps the updater's `cmd.exe`/`msiexec` launch and the `runas` elevation out of the binary that WACK scans. A runtime check alone would ship that code and rely on it never running. Microsoft warns that starting `cmd.exe` or PowerShell "could block your application from submission to the Microsoft Store" ([Prepare to package](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare)). The option sits beside `CMakeLists.txt:107-123`, implies `DISABLE_UPDATE_CHECKER`, adds a `PHRAMER_STORE_BUILD` definition, and **fails configuration loudly if `USE_PORTABLE_CONFIG` is ON**, because portable mode writes `phramer.ini` beside the exe (`src/utils/confighandler.cpp:304-306`). Failing is better than silently overriding the flag: the cache default is ON on Windows, and CLAUDE.md already records that variable as a trap. A new Windows-only helper, `src/utils/packageidentity.{h,cpp}`, is registered under `IF (WIN32)` in `src/utils/CMakeLists.txt:52-63`. It exposes `isPackaged()`, `packageFamilyName()` and `appUserModelId()`. `isPackaged()` uses the documented test: `GetCurrentPackageFullName` returns `APPMODEL_ERROR_NO_PACKAGE` when the process has no identity ([Detect package identity](https://learn.microsoft.com/windows/msix/detect-package-identity); [GetCurrentPackageFullName](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getcurrentpackagefullname)). The AUMID comes from `GetCurrentApplicationUserModelId` ([appmodel.h](https://learn.microsoft.com/windows/win32/api/appmodel/#functions)).

The existing switch is **broken today, and Phase 1 must fix it before anything depends on it**. In `src/core/flameshotdaemon.h:131-139`, `m_notificationFile` (the "Show in folder" target) sits inside `#if !defined(DISABLE_UPDATE_CHECKER)`, yet `flameshotdaemon.cpp:309` and `:700-701` use it unconditionally, so `-DDISABLE_UPDATE_CHECKER=ON` does not compile. The same guard also wraps `OPTION("checkForUpdates")` at `confighandler.cpp:83-85` and its getter at `confighandler.h:116-118`. An MSI user who moves to the Store build and still has `checkForUpdates=false` in `phramer.ini` would then hit `checkUnrecognizedSettings` (`confighandler.cpp:763-797`) and a visible config error. That breaks CLAUDE.md's "never remove a key that shipped" rule. The fix moves `m_notificationFile` out of the guard and keeps the OPTION and the getter/setter unconditional; only the behaviour and the Settings checkbox stay guarded. This also repairs the Nix and Arch packages, which already pass the flag (`flake.nix:86`, `PKGBUILD:37`).

Microsoft's guidance supports each replacement. Startup tasks: "If RequestEnableAsync is called from a packaged desktop app, no user-consent dialog is shown", the user must launch the app once, and "if a user disables a task, you can't programmatically re-enable it" ([StartupTask class](https://learn.microsoft.com/uwp/api/windows.applicationmodel.startuptask?view=winrt-28000); [Desktop packaging extensions](https://learn.microsoft.com/windows/apps/desktop/modernize/desktop-to-uwp-extensions#start-your-application-in-different-ways)). The settings checkbox should therefore map `DisabledByUser` to unchecked-and-disabled with a pointer to `ms-settings:startupapps` ([ms-settings URI reference](https://learn.microsoft.com/windows/apps/develop/launch/launch-settings#ms-settings-uri-scheme-reference)). The `startupLaunch` key stays as the user's intent. Declare the task `Enabled="false"` and call `RequestEnableAsync()` from a pre-checked "Launch at startup" box in the welcome tour. That keeps today's default-on behaviour while giving reviewers an explicit act of consent, which the silent default does not. The WinRT calls must run off the GUI STA, mirroring `snippingtool.cpp:39-58`. For ms-screenclip, `ASSOCSTR_APPID` returns "the AppUserModelID of the app associated with the… URI scheme" ([ASSOCSTR](https://learn.microsoft.com/windows/win32/api/shlwapi/ne-shlwapi-assocstr#constants)). The `registeredAUMID` deep link opens the app's own Default-apps page on Windows 11 21H2/22H2 with the April 2023 update or later. It may need `MaxVersionTested` of at least `10.0.22621.1555` after an OS upgrade, and should fall back to plain `ms-settings:defaultapps` ([Launch the Default Apps settings page](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-default-apps-settings)). For restart, AUMID activation is preferred over the Windows App SDK's `AppInstance::Restart()`, because that call terminates synchronously and would bypass CLAUDE.md's "quit, release the lock, then relaunch" ordering. `CoreApplication::RequestRestartAsync` needs a foreground window that a tray app lacks ([RequestRestartAsync](https://learn.microsoft.com/uwp/api/windows.applicationmodel.core.coreapplication.requestrestartasync)). For Store updates, "call the RegisterApplicationRestart function in every process that you want to restart… your application has 30 seconds to close" ([Desktop packaging extensions](https://learn.microsoft.com/windows/apps/desktop/modernize/desktop-to-uwp-extensions#start-your-application-in-different-ways)).

The CLI defect deserves its own note because it is real for the MSI too. `windows-cli.cpp:31` computes `int cmdSize = 32 + sizeof(directory) + sizeof(args);`. That is the size of two `std::wstring` objects, not their lengths, so the buffer is roughly 96 wide characters. A `C:\Program Files\WindowsApps\<Name>_15.0.0.0_x64__<hash>\` path plus arguments overflows it, `swprintf` fails, and `phramer-cli.exe` silently does nothing. Build the command as a `std::wstring` instead. The second-launch gap matters for certification: `main.cpp:391-394` exits quietly when a primary instance exists. Testers launch through the Start tile, and WACK's launch test uses `IApplicationActivationManager::ActivateApplication` ([WACK tests](https://learn.microsoft.com/windows/uwp/debug-test-perf/windows-app-certification-kit-tests)). A tray-only app that shows nothing invites a 10.1.1 "value proposition… clear during the first run" or 10.1.2 "fully functional" finding ([Store Policies 10.1](https://learn.microsoft.com/windows/apps/publish/store-policies)). Before returning, send the primary instance a message (`kdsa.sendMessage`) that opens the launcher or Settings.

### Config, AppData and side-by-side behaviour need testing more than coding

With `USE_PORTABLE_CONFIG=OFF`, `QSettings(IniFormat, UserScope, "phramer", "phramer")` resolves to `%APPDATA%\phramer\phramer.ini`, which works under MSIX with a twist. "New files and folders created under… Local… Roaming… are redirected to a per-user, per-package private location", while existing files are opened from the real location with "no virtualization for that file" ([Behind the scenes](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)). A fresh Store user's INI therefore lives under `%LOCALAPPDATA%\Packages\<PFN>\LocalCache\Roaming\phramer\` and is deleted on uninstall. A migrating MSI user's file is read in place. Qt 6.9.3's `QSettings` saves through `QSaveFile`, which writes a temp file and renames it ([qsettings.cpp @ 6.9.3](https://github.com/qt/qtbase/blob/6.9.3/src/corelib/io/qsettings.cpp)). Because that temp file is "new", the first save might leave a private copy that shadows the real file. Microsoft does not document this. If on-device testing shows the shadowing, `QSettings::setAtomicSyncRequired(false)` forces in-place writes. The KDSingleApplication key `com.phramer.Phramer` is shared with the MSI build, so the two editions should exclude each other rather than both grabbing Print Screen. The lock file under a possibly redirected `%TEMP%` makes that worth checking. Screenshots saved to Pictures, the Desktop or a user folder are never virtualized, so copy-as-file (CF_HDROP) to Teams and Outlook keeps working. "Open With" writes a temp PNG (`openwithprogram.cpp:22-43`). Whether `%LOCALAPPDATA%\Temp` is redirected is contested: Microsoft's list says "Local" without exception, while Advanced Installer says temp writes are not redirected ([Advanced Installer: MSIX temp folder](https://www.advancedinstaller.com/msix-temp-folder-access.html)). The fallback is to write to the save path.

## A hand-written manifest and a separate CI job produce the package

CPack has no MSIX generator, so packaging is a separate step that consumes `cmake --install` output. That leaves the WiX and ZIP logic, `CPACK_WIX_UPGRADE_GUID` and the hard-coded package names in `Windows-pack.yml:153-163` untouched. The manifest is a template, `packaging/msix/AppxManifest.xml.in`. Its Identity Name, Publisher (`CN=<GUID>`) and PublisherDisplayName are copied verbatim from Partner Center's Product identity page, because "values in the manifest are case-sensitive. Spaces and other punctuation must also match" ([App package requirements](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements); [View product identity details](https://learn.microsoft.com/windows/apps/publish/view-app-identity-details)). Those strings are public, so they belong in GitHub repository variables (`vars.MSIX_*`), not secrets. Target `Windows.Desktop`, which Microsoft says to use "always" for packaged desktop apps; the device-family setting also keeps the package off other families ([Generating MSIX package components](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-manual-conversion); [Device family availability](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/upload-app-packages#device-family-availability)). Declare **only `rescap:runFullTrust`**. The default Windows build makes no network requests once the updater is gone: Imgur is `ENABLE_IMGUR OFF` and no Windows workflow enables it (`CMakeLists.txt:115-119`). So `internetClient` can be omitted, and policy 10.6 asks that capabilities "legitimately relate to the functions of your product" ([Store Policies 10.6](https://learn.microsoft.com/windows/apps/publish/store-policies)). Declare `<Resource Language="en-us"/>` only. Listing all 48 translations would make Partner Center propose 48 listing languages, and policy 10.7 would then expect localized descriptions ([Add and edit Store listing info](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/add-and-edit-store-listing-info)).

The recommended skeleton below follows Microsoft's documented forms. It uses `EntryPoint="Windows.FullTrustApplication"` throughout, as Microsoft's extension samples and KDE do. The newer `uap10:RuntimeBehavior="packagedClassicApp"` + `mediumIL` pair is equivalent; pick one form, because mixing contradictory forms is an error ([Application element remarks](https://learn.microsoft.com/uwp/schemas/appxpackage/uapmanifestschema/element-f-application#remarks)). `Parameters` on `uap3:Protocol` is "supported only for packaged, full-trust apps" and keeps `main.cpp`'s `--screenclip "<link>"` parsing intact. Execution aliases allow "a single app execution alias for each application in the package". The console CLI therefore gets its own hidden `<Application>` with `desktop4:Subsystem="console"`, so it inherits the terminal's stdout ([Desktop packaging extensions](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/desktop-to-uwp-extensions); [uap5:AppExecutionAlias](https://learn.microsoft.com/uwp/schemas/appxpackage/uapmanifestschema/element-uap5-appexecutionalias); [winapp CLI usage](https://learn.microsoft.com/windows/apps/dev-tools/winapp-cli/usage#shell-completion)). `MinVersion="10.0.19041.0"` covers Windows 10 22H2 and every Windows 11, and `MaxVersionTested="10.0.26100.0"` matches the runner SDK ([runner-images Windows2025](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md)).

Microsoft does say that "console apps will always be multi-instanced and must explicitly declare SupportsMultipleInstances" ([Application element remarks](https://learn.microsoft.com/uwp/schemas/appxpackage/uapmanifestschema/element-f-application#remarks)). `makeappx pack` schema validation and `Add-AppxPackage -Register` are therefore the acceptance gate for the manifest, not this report.

### The payload is the release install tree, minus two traps

Stage with `cmake --install build --config Release --prefix stage` and use `stage\bin\*` as the package root. Two traps apply. The first is windeployqt: `src/CMakeLists.txt:410-414` picks `--debug` unless `CMAKE_BUILD_TYPE` matches Release, which would put debug Qt DLLs into the package. WACK fails debug builds ("C++ apps that are built in a debug configuration will fail") ([Desktop Bridge app tests](https://learn.microsoft.com/windows/uwp/debug-test-perf/windows-desktop-bridge-app-tests#current-required-tests)). The job must pass `-DCMAKE_BUILD_TYPE=Release` and the script must assert that no `Qt6*d.dll` exists. The second is `windeployqt --compiler-runtime`, which bundles `vc_redist.x64.exe` for release builds ([windeployqt main.cpp](https://raw.githubusercontent.com/qt/qtbase/dev/src/tools/windeployqt/main.cpp)). Delete it in staging and copy the app-local CRT DLLs (`vcruntime140*.dll`, `msvcp140*.dll`) from `VC\Redist\MSVC\<ver>\x64\Microsoft.VC14x.CRT\` into the package root. Microsoft's guidance conflicts here. A 2016 KB says desktop packages "must" depend on `Microsoft.VCLibs.140.00.UWPDesktop` ([C++ Runtime framework packages](https://learn.microsoft.com/troubleshoot/developer/visualstudio/cpp/libraries/c-runtime-packages-desktop-bridge)). The current GDK guidance says that for VS 2015–2022 "the traditional redistributable and framework package forms are identical, and you can choose either" ([GDK framework packages](https://learn.microsoft.com/gaming/gdk/docs/features/common/packaging/packaging-framework-packages#visual-studio-c++-runtime)). App-local wins on cost: the package's own files come first in the packaged DLL search order ([DLL search order](https://learn.microsoft.com/windows/win32/dlls/dynamic-link-library-search-order#search-order-for-packaged-apps)), sideload tests need no framework install, and there is no version lag against VS 2022 or 2026 toolsets. The VCLibs dependency is the fallback if certification objects.

Visual assets are generated once from `data/img/app/Phramer.svg` and committed under `packaging/msix/Assets/`, so CI needs no SVG toolchain. The minimum is StoreLogo, Square44x44Logo and Square150x150Logo at scale-100, 200 and 400, plus `Square44x44Logo.targetsize-{16,24,32,48,256}` with `_altform-unplated` copies. Without the unplated set the taskbar icon "will get an undesirable backplate" ([Construct your Windows app's icon](https://learn.microsoft.com/en-us/windows/apps/design/style/iconography/app-icon-construction)). The existing `appicon-{16,24,32,48,256}.png` map directly onto those targetsize slots. Every image must stay under 204,800 bytes, and the PRI must have a default resource and no reverse map ([Desktop Bridge app tests](https://learn.microsoft.com/windows/uwp/debug-test-perf/windows-desktop-bridge-app-tests#current-required-tests)). Pack with `makepri createconfig /cf priconfig.xml /dq en-US`, then `makepri new`, then `makeappx pack /v /h SHA256 /d stage /p Phramer_x64.msix` ([MakeAppx](https://learn.microsoft.com/en-us/windows/msix/package/create-app-package-with-makeappx-tool); [Generating MSIX package components](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-manual-conversion)). MakeAppx does not produce the recommended `.msixupload`. That is a zip of the `.msix` and an optional `.appxsym` with the extension renamed, but a plain `.msix` upload is also accepted ([Package a desktop app in Visual Studio](https://learn.microsoft.com/windows/msix/package/packaging-uwp-apps#generate-an-app-package-upload-file-for-store-submission); [Upload MSIX app packages](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/upload-app-packages#upload-your-app)). Upload the plain `.msix` first; add `.appxsym` crash symbols later by building RelWithDebInfo PDBs.

CI gets **a separate `windows-msix` job**, not a third value in the existing `[portable, installer]` matrix, whose later steps branch only on those two values and hard-code names. The job reuses the Qt and Visual Studio setup steps. It configures with quoted arguments to dodge CLAUDE.md's PowerShell dash-token trap: `"-DPHRAMER_STORE_BUILD=ON" -DUSE_PORTABLE_CONFIG=OFF -DCMAKE_BUILD_TYPE=Release`. It then runs `packaging/msix/make_msix.ps1` and uploads the `.msix` as a workflow artifact. The same job is added to `Windows-release.yml` with `"-DRELEASE_VERSION=$version"`, so each `v*` tag yields matching MSI and MSIX builds. The MSIX is kept as an artifact rather than a release asset, so Store bits are not distributed publicly. Attaching it would not confuse the in-app updater, which only matches `.msi` and `.msi.sha256sum` (`flameshotdaemon.cpp:739-743`). The `windows-2022` runner the workflows already use carries a 10.0.26100 SDK, but glob the `Windows Kits\10\bin\10.*\x64` path rather than hard-coding it. Pin QHotkey, currently `GIT_TAG master` at `CMakeLists.txt:175`, to a commit so Store builds are reproducible. WACK stays local. Its documentation both requires "an active user session" and claims it can run unattended, and no source confirms it exists on hosted runners ([Windows App Certification Kit](https://learn.microsoft.com/windows/uwp/debug-test-perf/windows-app-certification-kit#validate-your-windows-app-using-the-windows-app-certification-kit-from-a-command-line)).

The publisher display name you choose at signup becomes one of the three manifest strings, so decide it before the first build. Use your personal name or a plain handle. These include… Desktop Bridge and Win32 products" ([Store Policies 10.5.1](https://learn.microsoft.com/windows/apps/publish/store-policies)). Phramer's Store edition has an easy policy to write. It makes no network requests and has no telemetry or account. Captures, OCR (Windows.Media.Ocr), UI Automation text reading and DWM window enumeration all run on-device, and images leave only when the user copies, saves or shares them. A `PRIVACY.md` published through GitHub Pages costs nothing. Writing `PrintScreenKeyForSnippingEnabled` directly is arguably an unsupported method even when it works. Deep-linking to Settings is compliant by construction.

GPL-3.0-or-later" ([Add additional information](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/add-additional-information)). ## Three open risks each have a fallback that still ships

**Risk 1: ms-screenclip.** Registration itself looks safe. `ms-screenclip` does not appear on Microsoft's reserved URI scheme list, and Windows silently ignores registrations only for reserved names ([Reserved file and URI scheme names](https://learn.microsoft.com/en-us/windows/apps/develop/launch/reserved-uri-scheme-names)). MakeAppx rejects only SMB, FILE, MS-WWA-WEB and MS-WWA ([MakeAppx](https://learn.microsoft.com/en-us/windows/msix/package/create-app-package-with-makeappx-tool)). Two unknowns remain, and no source resolves either. The first is whether Windows' own Print Screen and Win+Shift+S pipeline honours a user's choice of a *third-party packaged* handler, which works for the MSI build today. The second is whether a reviewer objects to an app claiming a Microsoft `ms-` scheme. Microsoft asks only that a protocol registrant "handle all URI launches for that type of URI scheme" and provide "the functionality that is expected" ([Handle URI activation](https://learn.microsoft.com/windows/apps/develop/launch/handle-uri-activation)). Phramer meets that: recording links go back to Snipping Tool, and everything else becomes a capture. **Fallback:** the manifest template carries the protocol block between markers, and `make_msix.ps1` can emit a no-protocol variant. The Store edition then reaches Print Screen through the global hotkey once the user turns off Windows' toggle via the Settings deep link, which is today's non-ms-screenclip path. The ms-screenclip UI hides itself whenever no protocol is declared. Mention the handler in the certification notes so a rejection names the protocol explicitly instead of failing vaguely.

**Risk 2: HKCU virtualization of the Print Screen key.** Microsoft's text says "all writes under HKCU" are virtualized ([Behind the scenes](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)). Its troubleshooting guide says writes to `HKCU\Software\<AppName>` "are not virtualized" ([MSIX troubleshooting guide](https://learn.microsoft.com/windows/msix/msix-troubleshooting-guide#runtime-and-virtualization-behavior)). A community report from an MSIX app found `HKCU\Environment` writes reached the real registry ([anthropics/claude-code#93152](https://github.com/anthropics/claude-code/issues/93152)). Both outcomes are bad for the current code. If the write is virtualized, Phramer's merged read-back reports success while Print Screen still opens Snipping Tool. If it is not, the change survives uninstall and leaves Print Screen dead. The design in this plan, **read but never write; deep-link to `ms-settings:easeofaccess-keyboard`**, is correct under either reading. The URI is documented ([ms-settings reference](https://learn.microsoft.com/windows/apps/develop/launch/launch-settings#ms-settings-uri-scheme-reference)), and the toggle there is labelled "Use the Print screen key to open screen capture" on current Windows 11 ([Microsoft Q&A](https://learn.microsoft.com/answers/a/12779044)). The only residual risk is UX: whether the page scrolls to the toggle is undocumented. **Fallback:** show the existing `printscreen-key.png` resource with the exact label text and a "restart required" note. Do not request `unvirtualizedResources`. Microsoft says it is for "certain types of desktop PC games… not intended to be used for other scenarios" ([restricted capabilities](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations#restricted-capabilities)).

**Risk 3: Flameshot name and listing similarity.** A listing titled "Flameshot" already exists as product 9NDMNZGSL4X0, describing itself as "the fastest and most powerful snipping tool alternative on the Microsoft Store". Its publisher could not be verified ([Flameshot listing](https://apps.microsoft.com/detail/9ndmnzgsl4x0?hl=en-US&gl=US)). Upstream lists no Store channel and publishes no trademark policy; its logo is under the Free Art License 1.3 ([flameshot-org README](https://github.com/flameshot-org/flameshot/blob/master/README.md)). Security researchers have documented the STORESOCKS campaign, which published trojanized, Store-signed utility MSIX packages impersonating screenshot tools ([Hexastrike: STORESOCKS](https://hexastrike.com/resources/blog/threat-intelligence/storesocks-microsoft-store-apps-deliver-a-go-backconnect-proxy/)). Policy 10.1.1 forbids "a name, images, or any other metadata that is the same as that of other products" and requires an accurate "relationship to other products" ([Store Policies 10.1.1](https://learn.microsoft.com/windows/apps/publish/store-policies)). The defensible posture uses a distinct name and icon (both already true) and keeps "Flameshot" out of the title, keywords and screenshots. Attribution goes only in the description: "Phramer is an independent fork of the open-source Flameshot project (GPL-3.0); it is not affiliated with or endorsed by the Flameshot developers." Publish the official Store link in the README, as GIMP does, so users can tell Phramer from impostors. **Fallback:**

- If "Phramer" cannot be reserved, contact Microsoft with the public GitHub history as evidence of prior use ([Reserve your app name FAQ](https://learn.microsoft.com/windows/apps/publish/publish-your-app/msix/reserve-your-apps-name#frequently-asked-questions)).
- If a reviewer rejects under 10.1.1, move the attribution to the Copyright field and the About box (GPL attribution must survive somewhere), resubmit, and reply to the report or write to reportapp@microsoft.com. Appeals averaged 2.37 days, and 623 decisions were overturned in the year to June 2026 ([Certification appeal process](https://learn.microsoft.com/windows/apps/publish/store-policies#certification-appeal-process)).

Optionally tell the Flameshot maintainers before launch.

Several secondary risks have equally cheap fallbacks:

| Secondary risk | Signal | Fallback |
|---|---|---|
| Tray-only first run reads as "not functional" | Start-tile launch shows nothing (`main.cpp:391-394`) | Second launch forwards to primary; welcome tour on first run; explicit certification notes |
| Two `<Application>` elements trip WACK or certification | WACK or report names it | Ship one Application; drop the CLI alias and document `phramer-cli` as MSI-only |
| App-local CRT rejected | Report cites the C++ runtime | Declare the `Microsoft.VCLibs.140.00.UWPDesktop` dependency and remove the DLLs |
| QSaveFile leaves a private INI shadowing the MSI user's file | Edits to the real `phramer.ini` stop taking effect | `setAtomicSyncRequired(false)` in the packaged build |
| `%TEMP%` redirected, so "Open With" target cannot see the file | Target app reports file not found | Write the hand-off file to the save path |
| Restart child loses identity | `GetCurrentPackageFullName` fails in the relaunched process | Already avoided by AUMID activation |
| MSI and MSIX installed side by side | Shared lock, two autostarts, two ms-screenclip handlers | Store edition detects the MSI and asks the user to uninstall it; never touch HKLM |

## Conclusion

Most of the work is not packaging. It is making Phramer honest about what it can change on the system. Every feature that breaks under MSIX broke the same way: the app wrote to a shared system location, the registry or Program Files, and assumed Windows would see the change. The Store edition replaces each write with a declaration (protocol, startup task, alias) or a hand-off to a Settings page. That is the posture Microsoft's 2023 defaults principles and policy 10.2.8 reward, and the same changes make the app's uninstall clean. The broken `DISABLE_UPDATE_CHECKER` switch and the CLI buffer bug fall out of the work as genuine upstream-quality fixes that benefit the MSI, Nix and Arch builds too.

The decisive uncertainty is empirical, not policy: whether Print Screen reaches a packaged ms-screenclip handler. One afternoon of sideload testing settles it, and the template's protocol markers make either answer shippable. Treat the first submission as a test. Microsoft permits a free "available but not discoverable, direct link only" listing ([Beta testing and targeted distribution](https://learn.microsoft.com/windows/apps/publish/beta-testing-and-targeted-distribution#targeted-distribution-with-a-link-to-your-app's-listing)), so certification feedback on the tray-only first run, the protocol and the attribution arrives before any public announcement. A later submission flips it to discoverable.
